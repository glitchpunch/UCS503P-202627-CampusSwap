# Plan 2 — Database + Server (API)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Checkbox steps. Each task: write the listed tests first, see them fail, implement, see them pass, commit.

**Goal:** A FastAPI server that stores rooms, students and swap requests in SQLite, runs the Plan 1 engine, and handles the full swap lifecycle: submit → match → confirm/decline → warden approve.

**Architecture:** `app/models.py` (SQLAlchemy tables) · `app/services/*.py` (all business rules; plain functions that take a DB session, no web code) · `app/routers/*.py` (thin HTTP layer: parse input, call a service, shape the output) · `app/main.py` (wires routers, serves `code/frontend/public`). Time is injected (`now` argument), so deadline logic is testable.

**Tech Stack:** fastapi 0.141.1, SQLAlchemy 2.0.52, uvicorn 0.52.4, httpx 0.28.1 (tests), pytest 9.1.1.

## Global Constraints
- Same as Plan 1, plus: every business rule lives in `app/services/`, never in routers.
- Passwords: `hashlib.scrypt` (n=2**14, r=8, p=1, 16-byte salt), stored as `scrypt$<salt hex>$<hash hex>`.
- Session token: `secrets.token_urlsafe(32)` in cookie `cs_session` (HttpOnly, SameSite=Lax). Only its SHA-256 is stored in the DB. Lifetime 12 h.
- Service errors raise `DomainError(status, code, message)`. The router layer turns them into JSON `{"error": code, "message": message}` with that status.
- Confirmation deadline: 48 hours after the match run.
- Request statuses: `open`, `matched`, `completed`, `withdrawn`. Cycle statuses: `proposed`, `confirmed`, `approved`, `dissolved`. Member responses: `pending`, `accepted`, `declined`.
- Tracking ID format: `CS-<year>-<id padded to 4>` e.g. `CS-2026-0007`.

## Tables (`app/models.py`)
`users` (single-table inheritance on `role`: `Student`, `Admin`; students add roll_no, gender, year, branch) · `hostels` (code, name, gender M/F, warden_name) · `rooms` (hostel, block, floor, number, seater 1–3, ac, washroom attached/common, tags) · `seats` (room, label, occupant → users, unique) · `swap_requests` · `preferences` (request, rank 1–5, room; unique per request on rank and on room) · `match_runs` · `swap_cycles` · `cycle_members` (gives_seat, receives_seat, response, received_rank) · `events` · `login_sessions`.

### Task 1: Models, database setup, password hashing, seed data
Files: `app/__init__.py`, `app/db.py`, `app/models.py`, `app/security.py`, `app/errors.py`, `seed.py`, `tests/conftest.py`, `tests/test_security.py`, `tests/test_seed.py`
Tests:
- `hash_password` then `verify_password` gives True for the right password and False for a wrong one. Two hashes of the same password differ (random salt).
- `seed(db)` creates ≥ 4 hostels, every seat has an occupant, 3 demo students (`student1..3@thapar.edu`) have no request, 1 admin exists, and the pre-built pool contains open requests.
- Running TTC on the seeded pool (through Task 3's service) yields one 2-cycle, one 3-cycle and one 4-cycle. (Asserted in Task 3.)

### Task 2: Requests (feature 1)
Files: `app/services/requests.py`, `tests/test_requests_service.py`
Interface: `submit_request(db, student, room_ids: list[int], now) -> SwapRequest`, `withdraw_request(db, student, now) -> SwapRequest`, `active_request(db, student) -> SwapRequest | None`.
Tests (each rule = one test; rejections check the error `code`):
- happy path → status `open`, tracking ID matches `CS-\d{4}-\d{4}`, preferences saved in rank order, a `request_submitted` event is written.
- `empty_list`, `too_many` (>5), `duplicate_room`, `own_room`, `unknown_room`, `wrong_hostel_gender`, `no_seat`, `already_active`.
- withdraw an open request → `withdrawn`. Withdraw while `matched` → `in_cycle`. Withdraw with none → `no_request`.

### Task 3: Matching run (feature 2)
Files: `app/services/matching.py`, `tests/test_matching_service.py`
Interface: `run_matching(db, admin, algorithm: "ttc"|"pairwise", dry_run: bool, now) -> MatchRun`.
Behaviour: expire overdue cycles first. Pool = open requests. Each preference becomes that room's seat ids (ascending), in rank order. Save a MatchRun (pool size, matched, yield, cycles by length, readable trace lines using tracking IDs). If not a dry run: create a `swap_cycles` row (deadline now+48h) with members, set requests to `matched`, write events. Only one run at a time (a lock → `run_in_progress`). Pairwise must be a dry run (`pairwise_must_be_dry_run`).
Tests: the seeded pool gives cycle lengths {2:1, 3:1, 4:1}; members receive the right seats; `received_rank` is correct; a dry run saves the MatchRun but creates no cycles and changes no statuses; pairwise dry run on the seeded pool matches fewer students than TTC; an empty pool gives yield 0 and no cycles; the trace mentions every cycle.

### Task 4: Confirm / decline / approve / expiry
Files: `app/services/cycles.py`, `tests/test_cycles_service.py`
Interface: `accept(db, student, cycle_id, now)`, `decline(db, student, cycle_id, now)`, `approve(db, admin, cycle_id, now)`, `expire_overdue(db, now) -> int`.
Tests: all accept → `confirmed`. One decline → `dissolved`, the decliner is `withdrawn`, the others go back to `open`. Approve before confirmed → `not_confirmed`. Approve → `approved`, seat occupants swapped, requests `completed`. Deadline passed → `dissolved`, pending members `withdrawn`, accepted members `open`. Acting on someone else's cycle → `not_member`. Answering twice → `already_answered`.

### Task 5: Read models for pages
Files: `app/services/views.py`, `tests/test_views_service.py`
Interface: `public_stats(db, now) -> dict`, `rooms_listing(db, student) -> list[dict]`, `student_dashboard(db, student, now) -> dict`, `admin_overview(db) -> dict`, `admin_requests(db) -> list[dict]`, `export_csv(db) -> str`.
Tests: rooms listing hides other hostels' gender, marks own room, counts "open to swap"; dashboard states: no request / open / matched (includes cycle members in order + deadline) / completed; overview KPIs match a run; the CSV has a header plus one row per request.

### Task 6: HTTP layer + static pages
Files: `app/deps.py`, `app/routers/{auth,public,student,admin}.py`, `app/main.py`, `tests/test_api.py`
Endpoints: see design spec §4. Admin routes need role admin (403 `forbidden`), others need login (401 `not_logged_in`).
Tests (TestClient): login sets the cookie and `/api/auth/me` works; wrong password → 401 `bad_credentials`; logout clears the session; a student calling an admin route → 403; full story over HTTP: submit → admin run → accept ×N → approve → dashboard shows `completed`; CSV download has content-type `text/csv`; `/` serves `login.html`.
